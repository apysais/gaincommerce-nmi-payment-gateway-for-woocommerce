# Apple Pay Fix Plan v2 — 07-20-2026 21:49

## Background

`doc/07-20-2026-21:26-apple-pay-fix-plan.md` (v1) fixed a real bug — a double
`CollectJS.configure()` race guarded by `window.nmiCollectJSBlocksConfigured` — and that
fix was verified fully applied, built, and committed (source, minified build output, and
`.asset.php` cache-busting hashes all match; `git log` shows a clean commit `fb00621`).

Despite that, a fresh on-device test (iPhone, iOS 18.7, Safari) after deploying v1 still
shows no Apple Pay button. Google Pay renders fine on the same page load. This doc covers
the investigation that followed and the v2 fix.

## What the v1 Fix Plan Got Wrong

v1 assumed `apple-pay-blocks.js` (a separate express-payment-method component) mounts
before `checkout-blocks.js` (the CC form) and both race to call `CollectJS.configure()`.

That premise doesn't hold on WooCommerce Blocks checkout:

- `src/Plugin.php`'s `init_blocks_support()` (hooked to
  `woocommerce_blocks_payment_method_type_registration`) only calls
  `$payment_method_registry->register(new NMI_Blocks_Payment_Method())`.
- `NMI_Apple_Pay_Blocks` and `NMI_Google_Pay_Blocks` are `use`-imported at the top of
  `Plugin.php` but **never passed to `->register()`**.
- Consequence: `NMI_Apple_Pay_Blocks::get_payment_method_script_handles()` — which is what
  would enqueue `assets/js/build/apple-pay-blocks.js` — is never invoked. The file is never
  loaded by the browser, and `registerExpressPaymentMethod('gaincommerce_nmi_apple_pay_express', ...)`
  inside it never runs. **`apple-pay-blocks.js` is dead code on Blocks checkout.**

There is only ever one component in play: `checkout-blocks.js`'s `CreditCardForm`, which:
- Renders `<div id="nmi-apple-pay-button-blocks">` directly (`checkout-blocks.js:842-849`,
  gated on `applePayAvailable`).
- Calls `CollectJS.configure()` exactly once in its own `useEffect`
  (`checkout-blocks.js:80-337`), with both `applepay` and `googlepay` in the same `fields`
  config.

The v1 flag/`setTimeout` changes are harmless (they correctly no-op since
`apple-pay-blocks.js` never runs) but they didn't — and couldn't have — fixed the real
symptom, because the premised race never happens on this checkout.

## Confirmed Root-Cause Evidence (post-v1 debug log)

A new debug log capture (device: iPhone, iOS 18.7, Safari 26.5.2, HTTPS, `isSecureContext:
true`, `ApplePaySession Available: true`, `canMakePayments(): true`) shows:

```
[..42]  AP NMI Blocks: Initializing CollectJS...
[..46]  AP NMI Blocks: ApplePaySession.canMakePayments() returned: true
[..49]  AP NMI Blocks: Including Apple Pay field in CollectJS config
        {selector:"#nmi-apple-pay-button-blocks", selectorFound:true, collectJSLoaded:true,
         isSecureContext:true, applePaySessionAvailable:true, applePayEnabled:"yes",
         country:"US", currency:"USD", price:"15.00"}
[..53]  AP NMI Blocks: Including Google Pay field in CollectJS config
[..573] AP NMI Blocks: fieldsAvailableCallback — Apple Pay button rendered: false
        {childCount:0, hasIframe:false}
```

Key facts this establishes:

1. **`CollectJS.configure()` runs exactly once** — the v1 fix is confirmed working; no
   duplicate/overriding configure call.
2. **`fieldsAvailableCallback` fires in ~530ms**, well under the 10s `timeoutDuration` — no
   timeout, no thrown JS error anywhere in the console.
3. **The `applepay` field renders zero children, no iframe** — CollectJS silently declines
   to render anything for Apple Pay in this call.
4. **Google Pay, configured in the exact same call, renders successfully** on the same page
   load (confirmed with the user separately).

Because Google Pay succeeds through the identical `configure()` call while Apple Pay in
that same call renders nothing, this rules out:
- Anything shared/global (Permissions-Policy for the whole iframe, stale build, the v1
  double-configure bug, `isSecureContext`/`canMakePayments()` — all already true/fixed).
- A build/deploy problem (verified byte-for-byte against git).

The failure is specific to how CollectJS evaluates/renders the `applepay` field for this
domain/account, and it fails **silently** — no error surfaces to the parent page's console,
consistent with a rejection happening inside CollectJS's own script or a cross-origin
iframe that the page's `console.error` override cannot observe.

## Secondary Issue Found (not the root cause, but incorrect and worth fixing)

`enqueue-scripts.php:139-145` sets:

```php
header('Permissions-Policy: payment=(self "https://collectcheckout.com")');
```

`collectcheckout.com` appears nowhere else in either NMI plugin, doesn't match any known
NMI domain (`secure.nmi.com`, `networkmerchants.com`, `sandbox.nmi.com`), and `git log -p`
shows it was introduced, unverified, in the original "add google and apple pay" commit.
Since Google Pay renders fine, this header is not the cause of the Apple Pay symptom — but
it's still an unverified/likely-wrong origin and should be corrected as hardening.

Related stale comment: `enqueue-scripts.php:108-109` claims "Apple Pay button style is also
set here via `data-field-apple-pay-style-*` attrs," but no such attributes are ever added
anywhere in the file. The comment describes code that doesn't exist.

## Investigation Steps (do before/alongside the code change)

1. **Rule out "no card in Apple Wallet" cheaply.** `ApplePaySession.canMakePayments()` only
   checks device capability, not whether a card is provisioned. Confirm the test iPhone has
   an active card in the Wallet app.
2. **Add a network-level diagnostic** (Change 1 below) so we can see, from our own debug
   panel, whether CollectJS even attempts an Apple merchant-validation network round trip —
   without needing Mac Safari remote debugging.
3. **Escalate back to NMI support** with this sharper evidence: single `configure()` call,
   `applepay` field included, `fieldsAvailableCallback` fires at ~530ms with no timeout,
   `childCount: 0`/`hasIframe: false`, no console errors, Google Pay renders fine in the
   same call. Ask specifically what server-side condition causes CollectJS to silently
   render nothing for `applepay` under these conditions — e.g. a domain-verification state
   that looks "whitelisted" in the merchant-facing NMI dashboard but isn't actually
   propagated/verified with Apple, or an Apple Pay processor link that isn't actually active
   on the underlying merchant account despite the UI saying no activation is needed.

## Fix (Code Changes)

### Change 1 — Network-diagnostic logging in `fieldsAvailableCallback`

File: `src/blocks/checkout-blocks.js`, inside `baseConfig.fieldsAvailableCallback`
(~line 172, the block v1 added).

Extend the existing callback to sweep `performance.getEntriesByType('resource')` for any
request whose URL contains `apple`, `merchant`, or `session`, and log matches (name,
`initiatorType`, and `responseStatus`/`transferSize` where visible cross-origin) via
`console.log` / `NMI_Debug.addSystemInfo` — both already captured by
`nmi-payment-monitor.js`'s keyword filter ("Apple Pay" / "CollectJS" match).

### Change 2 — Fix the Permissions-Policy origin

File: `enqueue-scripts.php` (~line 144).

Replace the unverified `https://collectcheckout.com` origin. Since there's no live-inspected
confirmed iframe origin yet, widen to `payment=(self *)` to eliminate Permissions-Policy as
a variable entirely (cheap and safe — Google Pay already proves this isn't currently
blocking anything), then narrow back down once a real CollectJS iframe origin is identified
via Change 1's diagnostic. Also fix or remove the stale `data-field-apple-pay-style-*`
comment at lines 108-109.

### Change 3 — Build

```
npm run build
```

Regenerates `assets/js/build/checkout-blocks.js` and its `.asset.php` cache-busting hash
from Change 1.

2. Check the new resource-timing log entries:
   - **An Apple-related network request appears and succeeds** → button should now render;

   - **An Apple-related network request appears but fails (4xx/5xx/blocked)** → this is the
     concrete artifact to hand to NMI support to get the domain/merchant Apple Pay
     configuration fixed on their end.
   - **No Apple-related network request appears at all** → CollectJS is deciding not to
     attempt Apple Pay before even reaching the network for this domain/account — go back to
     NMI support with: "your SDK isn't even trying to validate the merchant for Apple Pay on
     this domain — why is Apple Pay disabled server-side for this account/domain given
     `enable_apple_pay=yes`?"
3. Confirm `Permissions-Policy` no longer risks blocking anything (should be moot given
   Google Pay already works, but this rules it out for good).
4. Re-confirm Google Pay still renders correctly (regression check on the shared
   `configure()` call).
